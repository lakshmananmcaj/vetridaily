# Festival Feature — Build Spec & Revenue Model

*Written 26 August 2026. Step 1 of the build order in `VETRIDAILY_GROWTH_PLAN.md`.*

**Short answer to "how does this earn?"** The festival screens do not sell anything by themselves.
They earn by creating **18+ high-intent moments per year** where you have a reason to reach a
devotee, and something relevant to offer them at that exact moment. Everything below is about
building those moments and what to put in them.

---

## 1. What you're building

Three screens, all client-side. The backend already exists and is public.

| Screen | Endpoint | Notes |
|---|---|---|
| Home card — "next festival" | `GET /api/spiritual/festivals/upcoming?count=3` | One card on the existing main screen |
| Festival list / calendar | `GET /api/spiritual/festivals/year/{year}`<br>`GET /api/spiritual/festivals/month/{m}/{y}` | Month + year toggle |
| Festival detail | `GET /api/spiritual/festivals/{slug}` | The screen that earns |

### What the API already gives you

`FestivalDetailDto` is richer than you'd expect — you do not need to write festival content:

| Field | Use it for |
|---|---|
| `FestivalNameTamil` | Primary heading — your audience reads Tamil first |
| `FestivalShortDescTamil` | List subtitle |
| `FestivalDetail` | Full body copy on the detail screen |
| `FeaturedImage` | Hero image **and** the share-sheet image |
| `UpcomingDates[]` | "Next: 14 Nov 2026" plus future years |
| `StartingTime` / `EndTime` | Muhurat window — high perceived value, drives return visits |
| `Slug` | Join key for product mapping, video mapping, deep links |
| `FestivalKeywords` | Play Store ASO + notification copy |

`StartingTime`/`EndTime` is the sleeper feature. Devotees check auspicious timing repeatedly on the
day itself, which turns one festival into several app opens.

## 2. Revenue stream A — contextual product sales

The core mechanism. A store tab gets ignored; a product surfaced *on the right day* converts.

### Festival → product map

Build this as a config table keyed on `Slug`. All seven products already exist as PDFs.

| Festival | Product to surface | Why it converts |
|---|---|---|
| Thai Poosam | **Temple-Travel-Guide-TN** | Peak kavadi/pilgrimage season — people are actively planning travel to Palani and Thiruchendur |
| Panguni Uthiram | **Marriage-Compatibility-Guide** | Celebrates Murugan–Deivanai marriage; families think about matches |
| Vaikasi Visakam | **Temple-Travel-Guide-TN** | Murugan's birth star — the year's biggest Murugan temple day |
| Skanda Sashti | *Sashti 6-day audio pack* (new) | Six-day observance; see stream B |
| Karthigai Deepam | **Vastu-Tips-Home** | Home-and-lamp focused festival |
| Tamil New Year | **Tamil-Panchangam-2026** | Year-ahead planning is the whole point of the day |
| Amavasai (monthly) | **Numerology-Guide** | Ancestor rites bring reflective, receptive users |
| Any birth-related | **Baby-Names-Book** | Namakaranam timing questions |

### Placement rules

- **One card**, below the festival body copy. Never an interstitial, never above the content.
- Copy names the benefit, not the format: "Plan your Palani trip" beats "Buy PDF (2.4 MB)".
- Suppress entirely for users who already own the product.
- Never show a product card on a mourning/ancestor observance without care — Amavasai is
  reflective, not celebratory. Test that one before shipping it.

### The funnel and its timing

```
Evening before (7–8 PM)   push: "Thai Poosam is tomorrow — timings inside"
        ↓
Festival detail screen     Tamil name, image, muhurat window, full description
        ↓
One product card           "Plan your Palani trip — Temple Guide ₹149"
        ↓
Play Billing               one-time INAPP purchase
        ↓
Server-verified download    DigitalStoreService delivers the PDF
```

The evening-before push matters more than anything on the screen. It is the difference between a
festival feature people discover and one that reaches them.

## 3. Revenue stream B — festival audio packs

Your daily audio pipeline already generates Tamil devotional audio. A festival pack is the same
pipeline pointed at a themed script.

**Skanda Sashti is the obvious first product.** Six days, six audios, sold as one pack — and you
already have `sashti-audio.m4a` sitting in the rasi repo. Sell it once a year at ₹99–₹199, released
day by day so buyers open the app six days running.

This is the only genuinely *new* content in the whole plan, and it is one script per day for six
days, generated by machinery you have already built and tested.

## 4. Revenue stream C — the Murugan temple directory

This one is nearly free and you may not realise you have it:

```
GET /api/temples?deity=Murugan&page=1&pageSize=20
GET /api/temples?deity=Murugan&city=Palani
GET /api/temples/{slug}
```

`TempleListDto` carries `NameTamil`, `DeityTamil`, `Location`, `City`, `ImageURL`, `Views`.
`TempleDetailDto` adds `Address`.

For a Murugan devotee app, an **Arupadai Veedu** screen — the six sacred abodes — is a headline
feature that costs one query parameter. Link each festival to its temples (Thai Poosam → Palani),
and put the Temple Travel Guide card on the temple list where intent is highest in the entire app.

It also feeds stream E: temple pages are exactly where a local business listing belongs.

---

## 5. Revenue stream D — video feed into your channel

```
GET /api/videos/recent?count=6
GET /api/videos?category=...
```

`VideoListDto` already carries `VideoURL`, `CategoryName`, `Views`, `Likes` and — notably —
**`IsPremium`**. You have a premium-video flag built and unused.

Two ways to earn:

1. **Free videos → YouTube AdSense.** Map festival `slug` → video, open with `vnd.youtube:` so the
   view lands in the signed-in native app and counts properly toward watch time.
2. **`IsPremium` videos → paid.** Long-form festival pooja guidance behind the same Play Billing
   entitlement as the PDFs. The flag exists; you only need to honour it client-side.

---

## 6. Revenue stream E — festival sponsorship from local business

You have `DirectoryController` with `categories` and `featured` — a business directory.

Tamil festivals are shopping seasons. Silk shops, jewellers, pooja-item stores and travel operators
all spend around Thai Poosam and Deepavali. A "featured near you" slot on a festival or temple page
is worth far more per impression than AdMob, because it is targeted by intent, region and date.

Honest caveat: **this needs real install numbers before anyone will pay.** Treat it as the year-two
stream, not the launch stream. But build the festival and temple screens knowing that slot goes
there, so you are not retrofitting later.

## 7. What this actually earns

Assumptions, stated so you can argue with them:

- Devotional push open rates run high — these are opted-in devotees, not a general audience. 15–25%.
- Contextual conversion at high intent: ~3% on major festivals, ~1% on monthly observances.
- Average product price ₹149. Google Play takes 15% on the first $1M/year.
- 6 major festivals + 12 monthly Sashti/Amavasai = 18 revenue events per year.

| Installs | Major festivals (6) | Monthly events (12) | **Net/year after Play fee** |
|---:|---:|---:|---:|
| 1,000 | ₹4,000 | ₹1,800 | **≈ ₹5,000** |
| 5,000 | ₹20,000 | ₹9,000 | **≈ ₹25,000** |
| 20,000 | ₹80,000 | ₹36,000 | **≈ ₹99,000** |
| 50,000 | ₹200,000 | ₹90,000 | **≈ ₹247,000** |

**Read this honestly.** At 1,000 installs this is roughly ₹400/month — not a business. The numbers
only become interesting past ~20,000 installs. That is not an argument against building it; it is
the argument *for* building it first, because:

- It scales linearly with installs while costing nothing per user
- It is the retention engine that grows installs in the first place
- It costs you almost nothing to build, since the entire backend exists

The festival feature's real financial value is **18 reasons a year to reopen the app**. Retention
feeds every other stream in the plan. Direct sales are a bonus on top.

## 8. Build checklist

**Client**
- [ ] Second Retrofit interface for `api.informationneeds.com` (separate base URL from Supabase)
- [ ] `FestivalListDto` / `FestivalDetailDto` / `TempleListDto` data classes
- [ ] Home card — next 3 upcoming festivals
- [ ] Festival list screen, month + year toggle
- [ ] Festival detail screen — Tamil name first, `FeaturedImage` hero, muhurat window, body
- [ ] Arupadai Veedu screen — `?deity=Murugan`
- [ ] Share sheet reuses the existing `share/` package with `FeaturedImage`
- [ ] Cache responses — festivals change rarely; a 24h disk cache makes the app work offline

**Monetization**
- [ ] Play Billing Library, one-time `INAPP` products
- [ ] `slug` → product id config table
- [ ] `slug` → video id config table
- [ ] Server-side purchase token verification before PDF delivery
- [ ] Entitlement check honouring `IsPremium` on videos

**Retention**
- [ ] Festival reminder scheduling via existing WorkManager setup
- [ ] Server push the evening before, via `PushNotificationService`
- [ ] Per-festival opt-out so reminders never feel like spam

**Ship order within this feature:** home card → detail screen → list/calendar → temples → billing.
The home card alone, showing the next festival with its Tamil name and date, is worth shipping on
its own before any of the rest exists.
